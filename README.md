# lifecycle-email-flows

A small, dependency-free Python model of lifecycle email automation, the kind of logic you configure in Klaviyo, Braze Canvas or Marketo: triggers, delays, branches, exits, frequency caps, suppression and quiet hours. It includes four flows, segment definitions, HTML email templates with Liquid-style personalization, a spec doc per flow, and a simulator.

**All data is synthetic.** Customers, events, products and the brand ("Northwind Goods") are generated or invented. Nothing here was exported from, imported into, or deployed on Klaviyo, Braze or Marketo. The flow specs in `docs/flows/` are labeled "modeled, not deployed" and are generated from the same JSON the engine runs.

## What is in it

| Path | What |
|---|---|
| `lifecycle/engine.py` | Event-driven flow runner. One time-ordered queue per customer, so caps count across flows. |
| `lifecycle/conditions.py` | Condition DSL for branches, trigger filters, exits (`did`, `count`, `segment`, `attr`, `trigger_prop`, `all/any/not`). Never sees events after "now". |
| `lifecycle/segments.py` | Quintile RFM scoring (6 named segments) and engagement tiers (highly_engaged, engaged, new, lapsing, dormant). |
| `lifecycle/templates.py` | Mini Liquid/Handlebars renderer: `{{ x \| default: "y" }}`, `money`, `{% if %}`, `{% for %}`, HTML escaping, strict mode. |
| `flows/*.json` | Welcome (3 touches), abandoned cart (2), win-back (2), post-purchase onboarding (2). |
| `templates/*.html` | 13 email bodies and a shared layout with unsubscribe link. |
| `docs/flows/*.md` | Canvas-style spec per flow (entry/exit table, step table, mermaid diagram, platform mapping), generated by `python -m lifecycle.specdoc --write`. |
| `lifecycle/simulator.py` | Seeded synthetic customers run through all flows; reports sends, suppressions, deferrals, exits. |

## Delivery rules (defaults in `Policy`)

Send order of checks: unsubscribed/bounced, no marketing consent, sunset tier (dormant, unless the flow allows it) -> quiet hours 21:00-08:00 customer-local (deferred, then re-checked) -> frequency caps (max 2 per 24h, 4 per 7 days, all flows combined). A suppressed send is skipped and the flow continues. Exit events (e.g. a purchase) are checked before every step.

## Run

```
python3 -m pip install pytest
python3 -m pytest
python3 -m lifecycle --customers 2000 --seed 7        # text report
python3 -m lifecycle --customers 2000 --seed 7 --json
python3 -m lifecycle.specdoc --write                  # regenerate docs/flows
```

## What is verified (by the tests)

- Template renderer: filters, escaping, conditionals, loops, strict-mode errors; all 13 templates render in strict mode with sample data and contain an unsubscribe link.
- Flow JSON validation: unknown nodes, unreachable nodes, cycles, missing templates, zero delays are rejected; shipped flows pass.
- Engine behavior on hand-built customers: welcome timing and branching, cart exit on purchase, trigger filter and re-entry window, quiet-hours deferral (and timezone effect), cross-flow frequency cap, unsubscribe/bounce/consent suppression, sunset with the win-back exception, win-back cancelled by a later order, first-order-only onboarding, no look-ahead, horizon and go-live cutoffs.
- Simulator: deterministic per seed; sent + suppressed = attempts; over 300 simulated customers no send falls in quiet hours, after an unsubscribe, without consent, or over a cap.
- Committed spec docs match what the generator produces.

## What is not claimed

- Simulated opens, clicks, carts and orders are generated up front and do **not** react to the emails, so the simulator reports engine decisions (what is sent or suppressed), not revenue, conversion lift or deliverability.
- RFM is a snapshot taken at the start of the simulated window; real platforms recompute continuously.
- No real sending, ESP integration, or MJML build. Templates are plain HTML with inline styles.
- Timestamps are naive UTC with whole-hour timezone offsets (no DST).
